The helper checks exactly four Flutter built-in guidelines:

```dart
extension AccessibilityTesting on WidgetTester {
  Future&lt;void&gt; testIfWidgetMeetsAccessibilityGuidelines(
    final Widget widget, {
    final AccessibilityFeatures? accessibilityFeatures,
    final AsyncWidgetTesterCallback? preparationCallback,
  }) async {
    binding.platformDispatcher.accessibilityFeaturesTestValue =
        accessibilityFeatures ?? const FakeAccessibilityFeatures();
    addTearDown(() {
      binding.platformDispatcher.clearAccessibilityFeaturesTestValue();
    });

    await pumpWidget(createTestWidget(widget));
    await preparationCallback?.call(this);

    await expectLater(this, meetsGuideline(androidTapTargetGuideline));
    await expectLater(this, meetsGuideline(iOSTapTargetGuideline));
    await expectLater(this, meetsGuideline(labeledTapTargetGuideline));
    await expectLater(this, meetsGuideline(textContrastGuideline));
  }
}
```

So the concrete checklist is:
1. **Tap targets ≥ 48×48 dp** (Android) and **≥ 44×44 pt** (iOS)
2. **Every tappable node has a semantics label** (`labeledTapTargetGuideline`)
3. **Text contrast meets WCAG AA** (4.5:1 normal, 3:1 large) — `textContrastGuideline`
4. Run with accessibility features **on** (`FakeAccessibilityFeatures`), torn down after

## (a) Transport: use plain stateless JSON per round, not the UI Message Stream

**Decisive facts:**

- **No first-party Dart/Flutter support exists.** Nothing on ai-sdk.dev documents non-JS clients. The stream-protocol page's only non-JS mention is a FastAPI *backend* example — guidance for non-JS *clients* is absent.
- **The `ai_sdk_dart` 2.0.0 family is not what it looks like.** Published by `hashstudios.dev` (not Vercel) despite branding itself a "port of Vercel AI SDK v6". I extracted the tarball: its `lib/src/` is `agent/core/messages/providers/...` — it **calls model providers directly**, so using it would put your AI Gateway key on the device. It contains **zero** references to `ui-message-stream`. Wrong tool entirely.
- **`ai_sdk_flutter` 0.1.2 is the only package that does the client-tool round trip** (`addToolResult`, `tool-input-available`, `tool-output-available`) — but it targets **AI SDK v5** and was last published 2025-11-19, with **49 downloads/30d and zero likes**. I diffed its chunk coverage against your installed `ai@7.0.77`: it knows ~20 chunk types; v7 emits ~48, including `tool-approval-request`, `tool-output-denied`, `tool-input-error`, and `reset-step`. You would own that gap.
- **The protocol is versioned but not stability-committed** (`x-vercel-ai-ui-message-stream: v1`); the docs state no deprecation policy.
- **The clincher:** per the SDK's own client-side-tool docs, even the React path *already* sends the full message list back to the server on every round. SSE buys you token-by-token text — which your UI does not render, since `ask_question` pauses the loop and the client shows a **widget**. You would take on a hand-rolled SSE parser to stream something no one sees.

**Recommendation:** POST `{messages, toolResult}` → server loops until the next `ask_question` or completion → returns `{messages, pendingCall}`. `dart:convert` + `package:http`, no new abstractions.

**Flutter team's recommendation, verbatim from the migration guide:** for new applications, use the standalone packages immediately, to avoid adopting deprecated code paths. Migration is `dart fix --apply --code=migrate_design_widgets` plus `flutter pub add material_ui cupertino_ui`.

**My recommendation for THIS app: go standalone `material_ui` (+ `cupertino_ui`), keep MaterialApp and M3 `ColorScheme.fromSeed`.** Reasoning:

- It's a **greenfield app** — the migration cost is one import line, and you'd otherwise write code that gets deprecation warnings in ~10 weeks. Your repo is `flutter analyze --fatal-infos`, so November's deprecation warnings become **hard CI failures**. That converts this from "nice to have" into "do it now or do it under duress in November."
- Design packages then ship **weekly**, decoupled from SDK bumps.

**Do NOT go raw-widgets-only (`flutter/widgets.dart` + `WidgetsApp`).** There is **no first-party or blessed** widgets-layer design-system framework — I looked, and the ecosystem answer is third-party (Mix, shadcn-style copy-paste) or roll-your-own. Going raw means you hand-build text fields, scrolling physics glue, dialogs/routes, ink/press feedback, and — the expensive one — **accessibility and localization plumbing** that Material gives you free. A journaling app's identity comes from typography, color and spacing, all of which `ThemeData` already expresses. ### (e) Things that contradict or complicate jumping to 3.47

Nothing blocks it, but four real snags:

1. **`google_fonts` 8.2.1 is the one genuine incompatibility risk.** It still targets Flutter `&gt;=3.38.0`, has no `material_ui` support in its changelog, and its public API exposes **`TextTheme`** (I confirmed ~17k `TextTheme` references in its API docs). `TextTheme` is a *Material* type — this is precisely the type-mismatch case the official guide flags: `MaterialUiCompatibilityBridge` supplies theme/localization data but **cannot resolve type mismatches** across the two libraries. So `GoogleFonts.baskervvilleTextTheme()` may not assign to `material_ui`'s `ThemeData.textTheme`.
   - **Mitigation is cheap and arguably better anyway:** for a single-family serif identity, use `GoogleFonts.baskervville()` which returns **`TextStyle`** (a widgets-layer type that crosses the boundary fine), and build your `TextTheme` yourself with `.copyWith`. Better still for a journaling app — **bundle the Baskervville TTFs as assets** and declare them in `pubspec.yaml`'s `fonts:` section, dropping `google_fonts` entirely. That removes the runtime HTTP font fetch, the `path_provider`/`crypto`/`http` transitive deps, the first-run flash of unstyled text, and this whole compatibility question. For one font family, the package is not carrying its weight.
2. **AGP 9 requirement** is the most likely build breakage on the jump from 3.44 — budget time for Gradle config, and note `emoji_picker_flutter` must be at 4.5.3 for its AGP 9 fix.
3. **iOS/macOS deployment target bump** needs Podfile + Xcode project edits.
4. **`emoji_picker_flutter` and `posthog_flutter` have not migrated** to `material_ui`. Both are lower-risk than `google_fonts`: PostHog is mostly non-widget API surface, and the emoji picker's config types are its own. If either leaks a Material type at the boundary, wrap with `MaterialUiCompatibilityBridge` in `MaterialApp.builder`. Worth a `flutter analyze` spike before committing to the migration in one go.

**Suggested order:** bump `.fvmrc` to 3.47.2 and get the plain 3.47 build green (AGP 9 + iOS target) *first*, then do the `material_ui` migration as a separate commit — so a Gradle failure and a type-mismatch failure never land in the same diff.

Cloned to `/private/tmp/claude-502/-Users-petertrost-dev-emotely/3b9ef8a1-ce8e-4d79-ad45-0ceabd7660df/scratchpad/flutter-testing-concepts` (read-only, nothing modified). Repo has two parallel apps: `bloc_app/` and `riverpod_app/`, plus a shared `common/` package. Focus below is `bloc_app`.

## 1. Packages

- **`mockito` (^5.4.6) + `build_runner`** — not mocktail. (README says "mocktail" in one bullet; `pubspec.yaml` and every test say mockito. README is stale.)
- **`bloc_test` (^10.0.0)** for cubit/bloc unit tests
- **`very_good_analysis` (^10.0.0)**, `public_member_api_docs: false`, generated files excluded from analyzer
- `integration_test` from SDK — **not patrol**
- `build_verify` is in `dev_dependencies` but unused — skip it

## 2. Widget test shape

**Pump helper** — one `PumpApp` extension on `WidgetTester` in `test/helpers/pump_app.dart`, re-exported via `test/helpers/helpers.dart` (that file is literally one `export` line):

```dart
extension PumpApp on WidgetTester {
  static const _locale = Locale('de');   // non-English default is deliberate — catches hardcoded strings
  static const _localizationsDelegates = AppLocalizations.localizationsDelegates;
  static const _supportedLocales = AppLocalizations.supportedLocales;

  Future&lt;void&gt; pumpApp({required Widget widget, Locale? locale}) async {
    await pumpWidget(MaterialApp(
      locale: locale ?? _locale,
      localizationsDelegates: _localizationsDelegates,
      supportedLocales: _supportedLocales,
      home: widget,
    ));
  }

  Future&lt;void&gt; pumpAppWithRouter({required GoRouter router, Locale? locale}) async { /* MaterialApp.router */ }
}
```

- **No theme injection.** Localization + locale only. `pumpAppWithRouter` is the second entry point for route tests.
- The riverpod variant adds `List&lt;Override&gt; overrides = const []` and wraps in `ProviderScope`.

**Per-test local helper is mandatory** — every test file defines a `pumpTestWidget(WidgetTester tester, {...})` closure inside `main()`, in the same scope as the mocks so the mocks don't have to be passed in. Named parameters carry the variation.

**How blocs are provided — a clean two-tier split:**

| Level | Bloc strategy |
|---|---|
| **Screen/view** (`*_view_test.dart`) | **Mocked cubit** via `BlocProvider.value` — stub `state`, stub `stream` as `Stream.empty()` |
| **Leaf widget** (`challenge_card_test.dart`) | **Real cubit** (widget creates its own), assert via `context.read&lt;Cubit&gt;().state` |
| **Route** (`*_route_test.dart`) | **Real cubit + mocked repository** registered in `GetIt`, real `GoRouter` |

Mocked-cubit setup requires two things people forget:

```dart
void main() {
  provideDummy(const ConceptsState.initial());   // mockito needs a dummy for the non-nullable state type
  late MockConceptsCubit cubit;
  late MockGoRouter router;

  setUp(() {
    cubit = MockConceptsCubit();
    when(cubit.stream).thenAnswer((_) =&gt; const Stream.empty());  // else BlocBuilder hangs
    router = MockGoRouter();
    when(router.go(any)).thenAnswer((_) {});
  });

  Future&lt;void&gt; pumpTestWidget(WidgetTester tester) =&gt; tester.pumpApp(
        widget: InheritedGoRouter(
          goRouter: router,
          child: BlocProvider&lt;ConceptsCubit&gt;.value(value: cubit, child: const ConceptsView()),
        ),
      );
```

`InheritedGoRouter(goRouter: mockRouter, child: ...)` is his standard trick for asserting navigation without a real router.

**Route tests** register mocked repos into GetIt and tear down:

```dart
setUp(() {
  mockConceptsRepository = MockConceptsRepository();
  when(mockConceptsRepository.getConcepts()).thenAnswer((_) async =&gt; []);
  GetIt.I.registerSingleton&lt;ConceptsRepository&gt;(mockConceptsRepository);
});
tearDown(() =&gt; GetIt.I.reset());
```

**Finder style** — by frequency across `bloc_app/test`: `find.byKey` 56, `find.byType` 41, `find.text` 39, `find.byIcon` 6, `find.ancestor` 1.
- **Static `Key` constants live on the widget class**, not in the test: `static const submitButtonKey = Key('submitButton');` in `challenge_card.dart`. Tests do `find.byKey(ChallengeCard.submitButtonKey)`.
- Localized strings are asserted through the real l10n object, never hardcoded: `final context = tester.element(find.byType(ConceptsView)); expect(find.text(context.l10n.conceptsViewTitle), findsOneWidget);` — `tester.element(find.byType(WidgetUnderTest))` is the standard way to get a context.
- Widget properties read via `tester.widget&lt;FilledButton&gt;(finder).onPressed` for enabled/disabled checks.

**`pump()` vs `pumpAndSettle()`** — strongly biased to explicit `pump()`. `challenge_card_test.dart` alone has 21 `tester.pump()` and zero `pumpAndSettle`. `pumpAndSettle` appears in only 5 files, reserved for animated page transitions (`sections_view_test.dart`: 10) and route/navigation tests.

**Localization variants** — `ValueVariant` is his preferred way to run one test across locales, with the variant class declared **at the end of the file** and instantiated **outside** the test:

```dart
typedef ChallengeCardVariantSignature = ({Locale locale, String question, String option1, String option2});

class ChallengeCardVariant extends ValueVariant&lt;ChallengeCardVariantSignature&gt; {

}

testWidgets('displays question and options', variant: variant, (tester) async {
  final (:locale, :question, :option1, :option2) = variant.currentValue!;
  ...
});
```

## 3. Mocking

- **All mocks in one file: `test/mocks.dart`.** Explicit rule: *"Avoid adding the mocks to the respective test files. ONLY add them to the `mocks.dart` file."*

```dart
@GenerateMocks([CacheManager, Dio, GoRouter, HttpClientAdapter,
  ConceptCubit, ConceptsCubit, ConceptsRepository, RestClient,
  ChallengesCubit, ChallengesRepository])
class GeneratedMocks {}
```
Tests import `'../../mocks.mocks.dart'`.

- **What gets mocked:** repositories (in cubit + route tests), the retrofit `RestClient` (in repository tests), `Dio` itself (in rest_client tests), `GoRouter`, `CacheManager` (kills network image loading), and cubits (in view tests). Layer N's test mocks layer N+1 — a strict seam-per-layer discipline.
- `build.yaml` must scope the mock builder, otherwise it won't generate for integration tests:

```yaml
builders:
  mockito|mockBuilder:
    generate_for: [ 'test/**.dart', 'integration_test/**.dart' ]
```
- Integration tests get their **own** `integration_test/mocks.dart` (only `CacheManager` there).
- No hand-written fakes anywhere. No `registerFallbackValue` (mockito uses `provideDummy` instead).

## 4. Bloc unit tests

**Every cubit has a `blocTest` unit test** — 4 cubits, 4 test files, no exceptions. Style:

```dart
blocTest&lt;ConceptsCubit, ConceptsState&gt;(
  'emits [loading, error] when fetchConcepts fails',
  setUp: () =&gt; when(mockRepository.getConcepts()).thenThrow(Exception('Test error')),
  build: () =&gt; ConceptsCubit(mockRepository),
  act: (cubit) =&gt; cubit.fetchConcepts(),
  expect: () =&gt; const [ConceptsState.loading(), ConceptsState.error('Failed to fetch concepts')],
  verify: (_) =&gt; verify(mockRepository.getConcepts()).called(1),
  errors: () =&gt; [isA&lt;Exception&gt;().having((e) =&gt; e.toString(), 'error', 'Exception: Test error')],
);
```

- `expect:` matches **full freezed instances**, never individual properties (explicit rule).
- Initial state gets a plain `test()`, not a `blocTest`.
- Multi-step acts use cascade: `act: (cubit) =&gt; cubit..toggleAnswer('a1')..submit()`.
- `build: ChallengeProgressCubit.new` tear-off when there are no deps.
- Pure computed methods (`isCorrect`) get plain `test()` cases outside blocTest.
- `errors:` is used alongside `expect:` when the cubit rethrows.

## 5. Structure + naming

- `test/` mirrors `lib/` exactly, including `test/features/&lt;feature&gt;/view/widgets/`. Same for `integration_test/`.
- `test/helpers/pump_app.dart` + `test/helpers/helpers.dart` (barrel) + `test/mocks.dart` at the root of `test/`.
- **`group()` takes a class reference, not a string**: `group(ConceptsView, () {...})`, `group(ChallengeProgressCubit, () {...})`. Strings only for non-class subjects (`group('router', ...)`, `group('usernameProvider', ...)`) because instances print as "Instance of [...]".
- Nested groups per method: `group('toggleAnswer', ...)`, `group('submit', ...)`, `group('reset', ...)`.
- Test names are **plain declarative behavior sentences** — no given/when/then, no "should":
  - `'renders loading state'`, `'has correct title'`, `'shows empty state'`
  - `'emits [loading, loaded] when fetchConcepts succeeds'`
  - `'navigates to concept on concept tap'`
  - `'submit button is disabled when no answer selected'`
  - `'renders $ConceptView and fetches concept'` — string interpolation of the class name
- **No structural comments.** Explicit rule against "// Arrange", "// Act", "// verify xyz". Comments only when non-obvious, e.g. `// Called twice, because ConceptsRoute is stacked on ConceptRoute`.
- Shared fixture data (a `challenge`, a list of `concepts`) is a top-level `final` inside `main()` above the helper.

## 6. Coverage discipline

CI is `very_good test --coverage` + Codecov — **there is no hard 100% gate**:

```yaml
- run: dart pub global activate very_good_cli 0.25.0
- run: dart pub global run very_good_cli:very_good test --coverage -- --file-reporter=json:reports/test_report.json
- run: lcov --remove coverage/lcov.info '**.freezed.dart' '**.g.dart' '**/app_localizations*.dart' -o coverage/cleaned.info --ignore-errors unused
```

- `--min-coverage` appears **nowhere**. Codecov uses `target: auto, base: auto` (ratchet — don't regress vs. the base commit), not `target: 100%`.
- Generated files (`.freezed.dart`, `.g.dart`, `app_localizations*.dart`) are stripped from lcov **and** excluded in `codecov.yml`; `integration_test/**` is excluded from coverage entirely.
- Codecov flags + components per package (`bloc_app`, `riverpod_app`, `common`) with `carryforward: true`, so per-package CI can skip unchanged packages.
- Also gated: `flutter analyze .` and `dart format . --set-exit-if-changed`.
- Test results are converted to JUnit XML via `junitreport` and uploaded.

## 7. Integration tests

- Plain `integration_test` package + `IntegrationTestWidgetsFlutterBinding.ensureInitialized()`. Not patrol.
- **Robot pattern** — a `ChallengesRobot` class per flow in `integration_test/challenges_robot.dart`, holding `WidgetTester`. Finders are getters, actions are `Future&lt;void&gt;` methods that each end in `pumpAndSettle()`. Tests read as prose:

```dart
final robot = ChallengesRobot(tester);
await robot.pumpApp();
expect(find.byType(ConceptsView), findsOneWidget);
await robot.tapFirstConcept();
expect(find.byType(ConceptView), findsOneWidget);
await robot.navigateThroughSectionsToChallenges();
await robot.tapSubmitButton();
expect(robot.findIncorrectText, findsOneWidget);
```
Robot exposes `bool get isSubmitButtonEnabled =&gt; tester.widget&lt;FilledButton&gt;(findSubmitButton).onPressed != null;` and a `_findInFirstCard` scoping helper built on `find.descendant`.
- Only two tests: one navigation flow, one interaction flow. Assertions are `findsOneWidget` on screen types — coarse-grained on purpose.
- **The external API is NOT mocked in integration tests.** Real `Dio` + real `RestClient` hitting `https://raw.githubusercontent.com/peter-trost/flutter-testing-concepts/refs/heads/main/mock_concepts.json`. Only `CacheManager` is mocked (returns an empty `Stream&lt;FileResponse&gt;`) to stop image downloads. Real repos are registered into GetIt in `setUp`, unregistered in `tearDown`.
